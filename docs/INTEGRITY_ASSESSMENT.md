Read-only. No files changed. Every claim below is cited to a specific file:line read

**Actual access model** (from `db/seed/001_seed.sql:16-28`, not a generic template):
`OPS_MANAGER` owns a group of branches, `AREA_HEAD` oversees several `OPS_MANAGER`s,
`STORE_HEAD`/`STORE_TEAM` are assigned to one branch. Scope is resolved two ways —
`core.location.om_user_id` (automatic, one location → one OM) and `core.user_scope`
(explicit LOCATION/AREA/CLUSTER/ROUTE/ALL grants) — unioned in
`core.v_user_effective_scope` (`db/ddl/001_schema.sql:837-849`).

## 2. Top 5 integrity/scoping gaps

**1. RLS is enabled on the parent `stock_movement`/`count_session`/`order_line` but never applied to their monthly partitions individually.**
`db/ddl/001_schema.sql:829` and `0004_operational_rls_and_rpt.py:92,184-185` run `ALTER TABLE ... ENABLE/FORCE ROW LEVEL SECURITY` against the parent relation name only. Postgres does not cascade RLS enablement to child partitions — each is a separate relation. Verified empirically: `SELECT count(*) FROM core.stock_movement` returns `0` under a non-matching scope; `SELECT count(*) FROM core.stock_movement_2026_07` returns all 10,522 rows regardless of scope. **Failure mode**: normal API traffic never trips this (SQLAlchemy always queries the parent name), but any raw SQL, Cloud SQL Studio session, ad hoc script, or future reporting job that names a partition directly gets unscoped, cross-branch data with no error.

**2. `sold_out_event` already demonstrated the "FORCE RLS + missing command policy = silent no-op" failure mode once, live.**
`0010_sales_and_sold_out.py:69-84` enabled SELECT+INSERT with FORCE but no DELETE policy; CLAUDE.md's own migration changelog records that this made DELETE "silently affect zero rows," caught only by manually testing the Sales edit flow end-to-end, not by any automated test. `0014_sold_out_event_delete_policy.py` fixed it after the fact. **Why this is a top-5 item and not just history**: `count_session`/`order_line` currently have the *same* shape — SELECT+INSERT+UPDATE but explicitly no DELETE policy (`0004:86-104`, comment: "nothing in this phase deletes scoped rows"). If a future feature ever needs to delete a count session or order line, it will hit this exact silent-zero-rows failure again unless someone remembers this incident.

**3. `core.count_line` has no `location_code` column and no RLS policy — scoping is 100% a matter of application-code discipline.**
`db/ddl/001_schema.sql:581-590`. Today it's safe *in practice* only because every route that touches it (`app/api/v1/counts.py:139-152,155-190,211-247`) fetches the parent `count_session` first via `_get_session_or_404`, which *is* RLS-protected — an out-of-scope `count_id` 404s before any `count_line` query runs. But this is a convention, not a guarantee Postgres enforces. **Failure mode**: any future code path that queries `core.count_line` directly — a reporting endpoint, an analytics query, a bulk export — without first checking `count_session`'s scope would return cross-branch count data with zero errors or warnings.

**4. Five location-scoped tables have no RLS at all and aren't validated by any test, because nothing queries them yet.**
`forecast_line`, `fact_daily_store_item`, `delivery_schedule`, `calendar_location_event`, `item_location_param` (`001_schema.sql:358,365,424,451→490,345`) all carry `location_code` but were never added to `_scoped_rw_policies`. This is currently harmless — grepping all of `backend/app` for these table/model names returns zero query sites outside comments. But the session-variable mechanism (`app.location_scope`) is already active on *every* request via `get_db`, which creates a false sense that "scoping is handled" — it's handled per-table, opt-in, and these tables haven't opted in. **Failure mode**: whoever builds the order-ladder/forecast/replenishment feature (CLAUDE.md's stated core value) needs to remember to add RLS to these tables as part of that work — nothing will fail a test if they forget, because no test exists that could.

**5. `user_scope.scope_type` has no CHECK constraint and no Pydantic literal type — a bad value fails silently, not loudly.**
Column is a bare `VARCHAR(20)` (`001_schema.sql:107`), and the request body field is a bare `str` (`app/api/v1/users.py:80,96`), not `Literal["LOCATION","AREA","CLUSTER","ROUTE","ALL"]`. `core.v_user_effective_scope`'s UNION (`001_schema.sql:837-849`) and `resolve_effective_scope`'s `scope_type = 'ALL'` check (`app/auth/deps.py:86-94`) both do exact string matching. **Failure mode**: an admin typo — `"Location"`, `"ALL "` with a trailing space, `"AREAS"` — inserts successfully (no CHECK constraint blocks it), then matches none of the view's branches. The affected user logs in successfully and sees **zero locations everywhere in the app**, with no error message at any layer. This is the "silent failure instead of exception" pattern the whole session-variable approach is structurally prone to, materialized in the one place input isn't otherwise constrained.

## 4. Feasibility verdict: database-enforced access control

**This isn't a hypothetical migration — it's already built, for 4 of ~10 candidate tables, using exactly the mechanism you'd propose.** The single factor that most drives the answer for this codebase: **you're not deciding whether to adopt session-variable-based RLS, you're deciding whether to finish rolling out a pattern that's already proven itself in production-shaped use** (`stock_movement`, `count_session`, `order_line`, `sold_out_event` all use identical `_scoped_rw_policies`-shaped policies reading `app.location_scope`/`app.unrestricted`).

- **What RLS can express here**: everything the access model needs. LOCATION/AREA/CLUSTER/ROUTE/ALL all collapse to "is this row's `location_code` in a precomputed list," which is exactly `string_to_array(current_setting(...))` — no per-row recursive logic needed because `v_user_effective_scope` already flattens the hierarchy before the policy ever runs.
- **Identity reaching Postgres**: not via Postgres native roles-per-user (that would require a role per `app_user`, which doesn't scale and breaks pooling entirely). This codebase already made the right call: one shared unprivileged role (`cocoims_app`), identity carried via `set_config('app.x', v, true)` — the `true` (is_local) flag is what makes this safe under connection pooling, since it's cleared at COMMIT/ROLLBACK rather than living on the pooled connection (`app/core/db.py:70-78` explains this precisely, and it's correct). This is the actual cost center: **every scoped request pays 5 extra round-trip statements** (`apply_session_context`'s five `set_config` calls, `app/core/db.py:80-96`) plus one extra query to resolve scope (`resolve_effective_scope`, two queries — one for the `unrestricted` check, one for the location list). Cheap in absolute terms, but it's per-request overhead that a pure application-layer `WHERE location_code IN (...)` wouldn't have.
- **Object count**: grows with **tables**, not roles/users — each newly-scoped table needs 3-4 `CREATE POLICY` statements plus `ENABLE`/`FORCE`, a fixed cost regardless of how many users or roles exist. This is the right shape for a system with a handful of scoped tables and potentially thousands of users.
- **Honest downsides, already observed in this codebase, not theoretical**: (1) silent failures — the `sold_out_event` DELETE incident (Top-5 #2) is exactly "missing policy → 0 rows affected, no error," and it already happened once; (2) split logic — a reader has to check both the Python route *and* the DDL/migration file to know what's actually enforced, which is why this assessment took reading both; (3) Alembic doesn't model policies as first-class objects — they're raw `op.execute()` SQL strings (`0004:86-104`), so there's no `alembic history`-level visibility into "which tables have RLS" without reading migration bodies; (4) testing friction — `backend/tests/test_rls_bypass.py` exists, so this isn't undone here, but each new scoped table needs its own explicit bypass test, it doesn't come for free.
- **Interaction risks found**: materialized views **cannot carry RLS policies at all** (Postgres RLS applies to relations of kind `r`/partitioned tables, not `m`). `rpt.mv_daily_network` sidesteps this by being a network-wide aggregate with no per-location rows to leak — that's the right shape for a matview under this access model, but it means if a future scoped, per-location matview is ever wanted, RLS cannot be the mechanism; the refresh query itself would have to pre-filter, or the matview would need to sit behind a further-scoped view. One `SECURITY DEFINER` function exists (`audit.fn_capture`, `001_schema.sql:748`) — narrow blast radius, writes fixed audit rows from trigger context, not a cross-tenant read risk.
- **Effort and what breaks first**: extending coverage to the 5 tables in Top-5 #4 is small, mechanical, and low-risk *precisely because* the pattern is already proven — each is a copy of `_scoped_rw_policies` plus a decision on which of SELECT/INSERT/UPDATE/DELETE actually apply. What would break first if this were rushed is exactly the `sold_out_event` pattern: shipping SELECT+INSERT and forgetting UPDATE/DELETE until a real user hits it, because there is no test today that fails when a command-type policy is missing on a FORCE-RLS table.

## 5. Prioritized recommendations

### Fix regardless (real gaps in what exists today, independent of any architecture decision)

1. **RLS-enable+force every existing partition of `stock_movement`/`count_session`/`order_line` individually, and make future partition creation include it.** *(Top-5 #1)* Cost: low, mechanical, additive `ALTER TABLE` per partition, no data change. What breaks if skipped: nothing today (no code path hits a partition by name), but the exposure sits there indefinitely waiting for the first ad hoc query, admin tool, or reporting job that does.
2. **Add a CHECK constraint on `core.user_scope.scope_type` and tighten the Pydantic field to a `Literal`.** *(Top-5 #5)* Cost: trivial — one CHECK, one type annotation change. What breaks if skipped: the failure mode is uniquely bad because it's silent and total (affected user sees nothing, nowhere, no error) rather than loud — exactly the kind of bug that survives testing because nobody thinks to type a location code wrong on purpose.
3. **Write a regression test for the "FORCE RLS table has a policy gap on one command type" pattern, informed by the `sold_out_event` DELETE incident.** *(Top-5 #2)* Not a schema change — a test that, for every table with `FORCE ROW LEVEL SECURITY`, asserts a policy exists for every DML command the application (or its foreseeable next feature) will issue against it. Cost: low, one test file. What breaks if skipped: this exact bug reproduces on `count_session`/`order_line` the day either needs a DELETE.
4. **Set explicit `pool_size`/`max_overflow` in `app/core/db.py` and add `--max-instances` to the Cloud Run deploy command.** Not an integrity bug, but shares the "unconfigured DB-facing ceiling" root cause and is cheap to fix now versus debugging under real load later. Cost: low, config-only, zero behavior change to any request.

### Architectural choice (whether/how far to extend DB-enforced scoping)

5. **Extend RLS to `forecast_line`, `fact_daily_store_item`, `delivery_schedule`, `calendar_location_event`, `item_location_param` — but time it to land *with* the feature that first queries each one, not speculatively now.** *(Top-5 #4)* This is squarely a "finish the rollout" move, not a new architecture decision — the mechanism is proven. Recommending against doing it *now*: these tables have zero current callers, so there's no live risk yet, and adding policies to genuinely dead schema just adds surface area for the same "policy exists but is stale/wrong by the time real code arrives" risk this assessment is trying to reduce. Do it as a checklist item attached to the order-ladder/forecast work itself.
6. **Give `count_line` its own scoping story before any code queries it directly without going through `count_session` first.** *(Top-5 #3)* Two real options exist here — add a denormalized `location_code` column to `count_line` (enables a direct RLS policy, costs one column and a bit of write-time redundancy) versus leaving it as an RLS-less child table and enforcing "always join through `count_session`" as a code-review rule. Not resolved here: the first is more robust against future mistakes, the second is cheaper and matches how every current caller already behaves. This is a judgment call about how much to trust future code review versus wanting the database to make the mistake structurally impossible.

### What NOT to do

- **Do not move to per-user Postgres roles for identity.** It would not express anything the current session-variable approach can't, it breaks connection pooling (a pooled connection can't cheaply switch native role mid-session the way it switches a GUC), and it multiplies DB objects with user count instead of table count — this is the one "obvious-sounding" move worth actively recommending against.
- **Do not add RLS to `item_price`/`v_effective_price`.** These are reference/catalog data, not operational ledger rows — the access model (per CLAUDE.md's own ACCESS section and the roles seed) treats pricing as globally visible to anyone with `item.read`/`item.price.update`, not branch-filtered. Adding scoping here would be solving a problem the access model doesn't have.
- **Do not build a per-location matview for future dashboards using materialized-view RLS.** It doesn't exist in Postgres for relkind `m`. If a scoped matview is ever wanted, decide that separately — don't assume the existing pattern generalizes there.

### Fine as-is

- The append-only ledger enforcement (trigger + revoked grants, now doubled up with RLS too) — genuinely solid, multiple independent layers.
- The check-then-insert idempotency patterns on `stock_movement` and `count_session` — correctly backed by real UNIQUE constraints, not just an app-level check. (The unhandled-`IntegrityError`-under-true-concurrency edge case exists but is low-severity given the documented, reasonable assumption that these are human-typed submissions, not concurrent automated replay.)
- The uniform `get_db`/`require_permission` composition across every route — no route was found that skips scoping by using the wrong dependency.
- `location.is_active`/`is_orderable` as GENERATED columns — correctly prevents the specific hand-set-them-and-drift bug CLAUDE.md warns about.

**What I'd need to say more than I have**: `backend/tests/test_rls_bypass.py` was not read line-by-line, so this can't state precisely which of the gaps above it already covers versus doesn't — that would sharpen items 1 and 3 in particular. The SPEC's actual access matrix for `location_status_history`/`location_closure` (whether they're meant to be branch-scoped or intentionally network-visible reference data) also wasn't verified directly against SPEC §7.3's permission matrix — their lack of RLS is treated as probably-intentional but unconfirmed.
